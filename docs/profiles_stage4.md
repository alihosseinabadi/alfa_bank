# Этап 4 Профиль и контекст запроса для MVP

Компонент готовит UserProfile и RequestContext из проверенных каталога и истории.
Он не ищет и не ранжирует материалы. Простые правила разрешены кейсом; веса —
явные стартовые гипотезы, не результат обучения и не вероятность покупки.

## Запуск и демонстрация

В Ubuntu/WSL из корня репозитория:

```bash
conda activate alpha
python scripts/verify_catalog_bundle.py
python scripts/verify_user_history.py
python scripts/build_user_profiles.py
python scripts/verify_user_profiles.py
python scripts/inspect_user_context.py --demo
python -m pytest backend/tests -q
```

Демо использует только синтетические профили и материалы. Восемь сценариев:
новый пользователь с задачей; один курс; тысяча уроков одного курса; отрицательная
оценка; калькулятор без тем; неизвестный пользователь без задачи; смена задачи;
короткий необязательный онбординг.

Для локального приватного просмотра:

```bash
python scripts/inspect_user_context.py --user-key 'organizer:<UUID>' \
  --task 'Нужен шаблон договора' --formats document --time-minutes 10
```

По умолчанию user_key и идентификаторы продолжения редактируются в выводе.
Ключ `--private` разрешает полный локальный вывод; его нельзя публиковать.
Неизвестный user_key создаёт холодный старт. Это локальный интерфейс разработки,
а не авторизация: UUID архива не связывается автоматически с аккаунтом сайта.

## Исторический режим

```bash
python scripts/build_user_profiles.py --cutoff-month 2026-06 \
  --output-dir data/processed/profiles_historical
python scripts/verify_user_profiles.py --profiles-dir data/processed/profiles_historical
```

Дата приведена для проверки механики, не подобрана для улучшения качества.
Используются только evaluation_inputs, строго более ранние месяцы и пользователи,
известные в этих наблюдениях. Текущие состояния зачислений/продолжения не
подмешиваются. Будущая модификация оценки и неподтверждённая историческая
атрибуция курса не используются. Сохраняется ограничение текущего каталога:
исторические версии содержимого и доступов не восстанавливаются.

## Файлы и интерфейсы

Чистые функции в backend/app/ml:

- profile_contracts.py — профиль, явные настройки, свидетельства и контекст.
- profile_policy.py — веса, review четырёх активных шкал, версии и хеширование.
- user_profile.py — агрегация наблюдений и тем без файловых/DB зависимостей.
- request_context.py — текущая задача и ограничения отдельно от истории.

Файловый адаптер backend/app/data_preparation/profile_bundle.py проверяет входы,
группирует наблюдения, строит профили и публикует неизменяемый набор.

Основные вызовы:

```python
profile = build_user_profile(
    user_key, observations, materials, explicit_preferences, policy,
    history_bundle_id=history_id, catalog_bundle_id=catalog_id,
    cutoff_month=None,
)
context = build_request_context(
    profile, task, explicit_constraints, learning_state,
)
```

UserProfile содержит идентичность и версии входов, явные настройки, нормированные
тематические веса, отдельные отрицательные свидетельства, bounded material
evidence, поддержку по различным материалам, эвристическую уверенность, описательные
счётчики форматов, fallback названия и причины cold start.

RequestContext сохраняет task_text без изменения. query_text использует обрезанный
по краям task либо явно выбранные темы, затем интересы/названия как fallback.
Явные задача/темы обнуляют history_weight и удаляют supporting_interests и
avoidance_topics из запроса. Поэтому старая история не подавляет новую задачу.
Сам профиль не меняется. Размер списка тем берётся из policy.max_context_topics
через сохранённый context_topic_limit; явный override функции допустим.

При отсутствии пригодного запроса возвращаются fallback_required и один короткий
вопрос. Стартовую подборку и проверку слабого совпадения выполняет этап 5.

## Политика сигналов

| Свидетельство | Начальная сила |
|---|---:|
| Зачисление | 0.2 |
| Прохождение | 0.6 |
| Положительная явная оценка | 1.0 |
| Отрицательная явная оценка | 1.0 |

Сначала применяется dedup по observation_id; конфликтующие копии одного ID
отклоняются. Затем данные агрегируются по user–material:

- implicit = max(силы зачисления/прохождения);
- positive = max(implicit, сила положительной оценки);
- negative = max(силы отрицательных оценок);
- net = max(positive - negative, 0).

Уроки одного курса не суммируются без ограничения. Каждый материал даёт не более
одного положительного и одного отрицательного вклада до 1. Вклад поровну делится
между уникальными исходными темами. Тематические net и negative нормируются
раздельно. Обе стороны конфликта сохраняются; случайный порядок строк не выбирает
«последнее» мнение. Уверенность зависит от различных материалов и согласованности
свидетельств: n/(n+2) * |positive-negative|/(positive+negative). Один курс и тысяча
его уроков не создают высокую уверенность. Это эвристика, не калиброванная вероятность.

Отрицательная оценка урока может относиться к подаче/качеству, а не к теме.
avoidance_topics — мягкие свидетельства; avoidance_is_hard_filter всегда false.
Следующий этап не должен превращать их в запрет материалов. При явной задаче
эти сигналы вообще не передаются в RequestContext.

Review шкал включает активность, полный набор значений, текст вопроса группы
и тексты follow-up для каждого значения. Для четырёх проверенных групп
1–3 считаются отрицательными, 4–5 — положительными. Удалённая группа не включена.
Изменение текста/значений требует нового review и версии политики. RatingTags
не используются как контентные Tags. Неизвестные шкалы и неоднозначный material_key
не порождают темы.

Материал без тем может дать fallback собственного названия только при положительном
net, допустимости discovery и отсутствии состояния URL unavailable. Новые темы
не придумываются. Отрицательное свидетельство не превращается в положительный
title fallback.

## Явные предпочтения и продолжение

Можно передать стадию бизнеса, отрасль, опыт, бюджетное предпочтение, доступное
время, форматы и выбранные темы. Отсутствующие поля остаются неизвестными.
Формат не выводится из архива: в нём преимущественно курсы и уроки, без журнала
показов других форматов. observed_format_counts — только описательная статистика.

reset_inferred очищает вычисленные интересы; исходная история и фактический
прогресс не удаляются. В текущем режиме продолжение по-прежнему может показываться
как отдельный кандидат с обязательными проверками платформы.
В историческом режиме актуальный прогресс всегда исключён.

Кандидаты продолжения сохраняют конкретное зачисление и два флага обязательных
проверок. Право доступа, URL и гарантированный следующий урок не создаются.
Сервис должен передавать learning_state из того же проверенного bundle истории.

## Артефакты и воспроизводимость

Выходы локальны: data/processed/profiles/CURRENT и <bundle_id>/:
profiles.jsonl, audit.json, manifest.json. Папка исключена из Git.
Манифест закрепляет историю, каталог, review словарей, политику, cutoff,
явные настройки, хеши кода и файлов. verify_user_profiles реконструирует все
профили из источников и сравнивает их с сохранёнными.
Повторная сборка одинаковых входов должна дать тот же ID и файлы.
Ошибки входов не заменяют CURRENT.

Для приватного JSON с явными настройками есть --explicit-preferences;
ключи — user_key, значения — поля ExplicitPreferences.
Полный JSON ProfilePolicy можно передать через --policy. Словарь review шкал
должен соответствовать проверенной исходной схеме и смыслу вопросов.

## Соответствие онлайн-этапу кейса

В PDF кейса на странице 13 определены веса:
работоспособность 30%, качество рекомендаций/ответов 25%, архитектура и
документация 20%, персонализация/неполные данные 15%, объяснимость/следующий шаг 5%,
презентация 5%. Для трека 1 не требуются функции Telegram.

На этапе 4 проверяются запуск компонента, персонализация, холодный старт,
онбординг, происхождение сигналов и контекст следующих шагов.
Качество реальной выдачи, сравнение с тематическим бейзлайном, интерфейс,
однокомандный запуск всего продукта и презентация остаются задачами дальнейшей
сборки MVP. Общий онлайн-балл или рост конверсии этим этапом не доказываются.
