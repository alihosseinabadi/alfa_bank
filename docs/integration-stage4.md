# Этап 4: локальный ML-провайдер

При `ALFA_RECOMMENDATIONS_ENABLED=true` backend при старте проверяет и загружает локальный каталог и индекс, строит BM25 один раз в памяти и подключает PostgreSQL событий. HTTP-запрос проходит через анонимный профиль без истории, заданную задачу и ограничения, поиск BM25, признаки и prior из `ml`, восстановленное состояние shared LinUCB и штатный slate с `relevance_gap=0.15`. Реальные карточки из доступного каталога возвращаются API; frontend пока остаётся в деморежиме. Подтверждение показов, действия и запуск обработчика наград относятся к последующим этапам.

Провайдер использует отдельную событийную БД с миграцией `0005_serving_requests`. На `(actor_id, request_key)` берётся транзакционная блокировка; хэш нормализованного запроса и минимальный публичный ответ сохраняются в той же транзакции, что решение, карточки и seed. Идентичный повтор возвращает сохранённый ответ до повторного поиска, изменённый — 409. Если сохранение решения не удалось, выдача не публикуется. Сам факт выдачи не является показом.

Текущий `LearningService` использует собственные значения по умолчанию `alpha=0.5` и `ridge=1.0`; прежние переменные `RETRIEVER`, `LINUCB_ALPHA` и `LINUCB_RIDGE` не управляют этим провайдером. Состояние LinUCB восстанавливается из ledger; в процессе оно кэшируется и обновляется при изменении числа ревизий ledger под блокировкой, общей с обучением. Если состояние модели несовместимо, используется существующий prior с явным сообщением. Если каталог, индекс, версия миграций или сама событийная БД недоступны, сервис возвращает 503, а не фиктивные рекомендации. Проверка реконструирует индекс из публичных фрагментов на старте; ресурсы не перечитываются на каждый запрос.

## Подготовка из предоставленного архива

Входные файлы, промежуточные CSV, каталог, индекс, модель и векторы должны оставаться локальными и игнорируются Git. Нужны Docker, Python 3.12, Node для UI и зависимости `backend/requirements.txt` и `backend/requirements-catalog.txt`. Исходная база организаторов должна быть изолирована от продуктовой и событийной БД; экспорт каталога не выгружает историю пользователей.

Для новой рабочей копии, в которой целевые каталоги отсутствуют:

```bash
python -m pip install -r backend/requirements.txt -r backend/requirements-catalog.txt
mkdir -p data/raw
# Скопируйте предоставленный PostgreSQL backup в data/raw/alfa_course_hackathon.backup.
# Не перезаписывайте уже существующие пользовательские файлы.
python scripts/restore_catalog_source.py
python scripts/export_catalog_sources.py --compose-file scripts/catalog-source.compose.yml
python scripts/prepare_tokenizer_from_archive.py --model-zip /path/to/e5-model.zip --vectors-zip /path/to/e5-vectors.zip
# При недоступных локальных архивах есть альтернативный скачивающий путь:
# python scripts/prepare_catalog_tokenizer.py
python scripts/build_catalog_bundle.py
python scripts/verify_catalog_bundle.py
python scripts/build_retrieval_index.py
python scripts/build_retrieval_index.py --verify
```

Команда извлечения токенизатора сверяет модель, ревизию и SHA-256 с манифестом векторов и не извлекает веса; это проверка совместимости, не подтверждение подлинности архива. Строить индекс нужно в том же окружении NumPy/SciPy/scikit-learn, в котором он будет загружаться: версии сверяются строго. После экспорта исходную БД можно остановить `docker compose -f scripts/catalog-source.compose.yml stop`.

Далее скопируйте `.env.example` в `.env`, задайте случайный стабильный `ALFA_SESSION_SECRET` (например, `python -c "import secrets; print(secrets.token_urlsafe(32))"`), для локального HTTP установите `ALFA_SESSION_COOKIE_SECURE=false` и включите `ALFA_RECOMMENDATIONS_ENABLED=true`. На HTTPS оставьте secure cookie включённым. Два разных PostgreSQL должны быть доступны по адресам из `.env`:

```bash
set -a; source .env; set +a
docker compose up -d --wait db
docker compose -f scripts/events.compose.yml up -d --wait db
python -m alembic -c backend/product-alembic.ini upgrade head
python scripts/migrate_events.py
PYTHONPATH=backend uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Не используйте `alfa_events_test` как рабочую БД. Для демонстрации HTTP используйте [контракт v1](recommendation-api-v1.md): получить сессию, передать cookie, CSRF и стабильный UUID запроса. Существующий frontend-клиент пока не подключён к ленте.

## Данные и выбор канала

Из предоставленного архива построены 1 524 записи каталога и 9 982 публичных фрагмента; проверенный индекс включает 1 444 материала и 9 965 уникальных фрагментов. Аудит построения не обнаружил в нём защищённых фрагментов и платных тел материалов. Проверка хэшей и реконструкция доказывают согласованность файлов, а не подлинность источника: каталог должен поступать из доверенного источника, доступ к записи артефактов нужно ограничить.

Предоставленный E5-токенизатор совпал с указанным в манифесте векторов SHA и закреплённой ревизией. Векторы привязаны к другому ID индекса, поэтому их совместимость с текущим индексом не подтверждена и они не используются. Доступность URL при построении не проверялась: такие ссылки обозначаются `unknown`.

Выбран BM25 из ветки `ml`: в ранее задокументированной агентной оценке он лучше отказывал на контрольных запросах вне тематики; на текущем снимке для запроса о полёте к Луне TF-IDF выдал бизнес-материалы, а BM25 запросил уточнение. Эта диагностика не доказывает универсального превосходства. Семь новых запросов не имеют независимой разметки; на запрос клиентов интернет-магазина BM25 поставил первым материал о техническом задании, что выглядит слабым соответствием. На задачу об НДС первым оказался материал об НДС. Неразмеченные материалы не считались автоматически нерелевантными; коммерческий эффект не измерен.

В диагностическом прогоне пять бизнес-задач дали по одной карточке при запрошенных шести; два запроса вне тематики вернули уточнение. Более высокий `relevance_gap` в ранее проведённом маленьком эксперименте увеличивал выдачу, но снижал долю размеченных полезных материалов; поэтому значение не менялось и выдача не дополнялась произвольными карточками. Это известное ограничение качества, требующее новой независимой разметки и оценки.

## Проверки

Запустите `python -m pytest backend/tests -q` с изолированными `ALFA_EVENTS_TEST_DATABASE_URL` и `ALFA_PRODUCT_TEST_DATABASE_URL`; PostgreSQL-тесты создают временные схемы и не должны выполняться против исходной БД организаторов. Проверены конкурентные повторы, rollback после сохранения решения, повтор после изменения модели и перезапуска провайдера, fallback и несовместимость артефактов. Отдельно проверены реальный HTTP с запросом НДС, ограничением формата/доступа, 409 для изменённого payload, запросом вне тематики и повтором после рестарта процесса. При запуске без тестовых URL PostgreSQL-тесты пропускаются.

## Независимое ревью

Критик в роли lead backend engineer оценил этап на **8/10**: самостоятельно изучил код, запустил 10 PostgreSQL-тестов и проверил два реальных HTTP-сценария на тестовой БД. Он отметил ограничения качества, размера подборки, неизвестной доступности ссылок и отсутствие пользовательской истории, а также необходимость последующей проверки ролей PostgreSQL и независимой оценки на размеченном снимке. Происхождение локального каталога и HTTP-повтор после перезапуска он оценивал по результатам основного исполнителя.

Полный локальный регрессионный прогон — 266 backend/ML тестов прошли, включая тест токенизатора; 2 предупреждения зависимостей. Критик отдельно выполнил 10/10 тестов провайдера. HTTP-проверка с настоящим каталогом и перезапуском backend подтвердила сохранение ответа.
