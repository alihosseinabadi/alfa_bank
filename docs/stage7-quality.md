# Этап 7: проверка качества поиска

## Сопоставимый диагностический прогон

Для всех пяти методов использованы один локальный каталог и индекс (`index_bundle_id=c3a14357bcf26d48b6836cdd22d5361a1e52e85e9216a27ec86dcb379da68627`), одни и те же восемь синтетических задач (`dev001`, `dev002`, `dev004`, `dev005`, `dev010`, `dev012`, `test001`, `test002` из `data/synthetic/retrieval_cases_v2.json`), одинаковый контекст, фильтры и предел 50. Сравнивались topic baseline, TF-IDF, BM25 и оба метода с prior. Материалы взяты из реального каталога организатора; задачи искусственные, пользовательских историй или симуляции платежей в этих восьми задачах нет. Параметры не менялись. Это кандидаты до LinUCB и финального slate, не размер пользовательской выдачи.

Получено 132 уникальные пары задача–материал в объединённом top-10-пуле. Новая независимая разметка этих пар отсутствует. Ни одна неразмеченная пара не засчитана нерелевантной; количественные метрики качества на этом новом прогоне не вычислялись. Нижеприведённые примеры — предварительная экспертная диагностика по названию, а не независимая разметка содержания:

- Удачно выглядит задача об организационно-правовой форме: BM25 и TF-IDF поставили первым материал «Организационно-правовая форма».
- Задача об оценке спроса: BM25 поставил первым «Customer Development: как проверить спрос на продукт», что выглядит близким соответствием.
- Задача о бюджете запуска магазина: BM25 поставил первым «Списание товара на складе», TF-IDF — «Нейросети для бизнеса: с чего начать»; по названиям оба ответа выглядят слабыми для задачи.
- Задача о закрытии ИП: оба метода поставили первым материал о расчёте себестоимости маникюра. Это явный диагностический промах по названию, но не оценка остальных результатов.

Prior не менял первый результат в этих восьми случаях. Число кандидатов не является мерой релевантности: например, BM25 часто достигает предела 50. Ранее отмеченная короткая финальная выдача и `relevance_gap=0.15` этим прогоном не переоценивались.

## Ранее зафиксированные оценки

В [отчёте 14 ноября](quality_stage56.md) на 21 содержательной задаче, с 160 размеченными парами и одним агентным оценщиком, зафиксированы NDCG@10: TF-IDF 0,8321, TF-IDF + prior 0,8326, BM25 0,8564, BM25 + prior 0,8567; успех@5 — 19/21 у всех четырёх. На пяти новых holdout-задачах TF-IDF имел NDCG@10 0,8326, BM25 — 0,8190. На семи проверочных задачах BM25 отказал 7/7, TF-IDF 5/7. Это исторические метрики на ранее замороженном наборе, не результат текущих восьми задач и не доказательство универсального превосходства BM25. Исходные приватные оценки и замороженная коллекция в текущей копии отсутствуют: повторный пересчёт тех метрик не выполнен. Отчёт описывает частичную пуловую разметку, а не весь каталог; новые/неразмеченные материалы остаются неизвестными.

E5 и гибрид не сравнивались: совместимость локальных векторов с текущим индексом не подтверждена. Не измерялись онлайн-качество, продажи и конверсия; выводы по пользователям или бизнес-эффекту невозможны.

## Как повторить текущую диагностику

Нужны локально подготовленные каталог и индекс из [инструкции этапа 4](integration-stage4.md), Python-зависимости проекта и достаточно места во временном каталоге. Команды создают новую временную директорию и не перезаписывают прежние оценки. Результаты содержат фрагменты каталога и должны оставаться локально, вне Git.

```bash
QUALITY_DIR=$(mktemp -d)
export QUALITY_DIR
python - <<'PY'
import json, os
from pathlib import Path
p = Path(os.environ['QUALITY_DIR'])
cases = json.loads(Path('data/synthetic/retrieval_cases_v2.json').read_text())
ids = {'dev001','dev002','dev004','dev005','dev010','dev012','test001','test002'}
(p/'cases.json').write_text(json.dumps([c for c in cases if c['case_id'] in ids], ensure_ascii=False))
(p/'extra.json').write_text('[]')
(p/'seeds.json').write_text('[]')
PY
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python scripts/evaluate_stage56.py collect \
  --eval-dir "$QUALITY_DIR/run" --base-cases "$QUALITY_DIR/cases.json" \
  --extra-cases "$QUALITY_DIR/extra.json" --seed-labels "$QUALITY_DIR/seeds.json"
```

Идентификатор конкретного собранного пула: `b7933c31ec1ed21f6ef92230003b1ed7d761d722024d02463d790bae0be6ba9d`. Манифест фиксирует хэши входов и кода; изменения окружения или артефактов могут изменить идентификатор. Команда `score` требует полную локальную разметку пула и без неё не применялась.
