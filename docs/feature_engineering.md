# Признаки пары запрос материал для MVP

Актуальная реализация этапа 6: backend/app/ml/feature_registry.py,
feature_engineering.py и prior_ranking.py. Версия pair-features-v1.
Старая проектная схема 39 признаков для шести искусственных категорий
не соответствует реальному каталогу и не используется.

## Схема

22 nullable-признака, порядок фиксирован в FEATURE_NAMES.
Вектор float32: bias=1, затем 22 значения, затем 22 маски наличия.
Итого 45 компонент. Пропуск хранится как null; в векторе значение 0
с маской 0. Известный ноль получает маску 1.
Все значения конечны и лежат в [0,1]; порядок и правила входят в хеш реестра.

| Признак | Смысл и источник |
|---|---|
| retrieval_rank_score | 1/log2(rank+1), позиция в выдаче одного выбранного retrieval |
| task_text_overlap | Доля различных слов текущей задачи в публичных фрагментах |
| explicit_topic_match | Доля явно выбранных тем, совпавших с темами материала |
| history_topic_match | Совпавшая масса разрешённых контекстом положительных тем профиля |
| history_support | n/(n+2) по различным подтверждающим материалам; эвристика |
| avoidance_topic_match | Совпавшая масса разрешённых отрицательных тем; мягкий сигнал |
| format_match | Совпадение явно заданного формата; иначе null |
| open_access | Условия доступа из каталога, отдельно от цены |
| duration_fit | Известная длительность подходит заданному времени; иначе null |
| listed_price_scaled | min(цена/10000,1), только диагностический признак |
| industry_match | Точное нормализованное совпадение явной отрасли с исходной меткой |
| stage_match | null: проверенных меток стадии у материалов пока нет |
| experience_match | null: проверенных меток уровня у материалов пока нет |
| seen_before | Есть запись о взаимодействии; отсутствие записи остаётся null |
| completed | Известное состояние завершения из совместимого снимка прогресса |
| progress_fraction | Максимальная доля завершённых активных листовых уроков по привязкам |
| public_evidence | Проверенный публичный scope всех использованных свидетельств |
| metadata_only | Все использованные свидетельства являются метаданными карточки |
| url_reachable | 1 только для reachable; временные ошибки и непроверенные URL дают null |
| tfidf_similarity | Косинус TF-IDF своего канала, без смешения шкал |
| e5_similarity | (cosine+1)/2, диагностический, не вероятность релевантности |
| bm25_saturation | score/(1+score), диагностический, без калибровки |

Полные типы, диапазоны, пропуски, источники и порядок экспортируются командой:

```bash
python scripts/rank_materials.py --export-registry
```

## Скоринг начальной политики

Положительные компоненты по умолчанию:
1.0 * retrieval_rank_score + 0.10 * task_text_overlap +
0.10 * explicit_topic_match + 0.15 * history_weight *
history_topic_match * history_support + 0.05 * industry_match +
0.02 * duration_fit.

Отрицательные: 0.05 * history_weight * avoidance_topic_match и
0.03 * history_weight * completed. История активна только при источнике
inferred_topics/material_titles и history_weight>0. При явной задаче или
явных темах исторические компоненты равны нулю. Пропуск компонента даёт
нейтральный вклад 0; известная подходящая длительность даёт небольшой бонус.

Веса — стартовая конфигурация, не результат обучения или настройки по test.
Сырые оценки TF-IDF, BM25, E5 и RRF не складываются между собой.
Цена, предположение о платежеспособности и неподтверждённый уровень не
влияют на порядок. Оценка может превышать 1 и не является вероятностью.
Равенства разрешаются по canonical material_key.

## Происхождение и совместимость

PairFeatures содержит context_id, profile_version, index_bundle_id,
catalog_bundle_id, retrieval_policy_id и registry_hash. Итог также содержит
policy_id, метод/параметры retrieval, причины и исходные оценки каналов.
Сохранённый локальный bundle включает реестр, политику, результат,
хеши файлов и кода. Эти снимки можно будет связывать с показами на этапе 7;
сейчас показов и обучающих обновлений нет.

Не использовать текущий learning_state в историческом контексте.
Не выводить точный порядок событий из месячных дат архива.
Отсутствие меток отрасли/стадии/опыта не является плохим совпадением.
Изменение списка, порядка или семантики признаков требует новой версии,
нового хеша и отдельной совместимости будущей модели.
