# Интеграция веток: этап 2

`integration/mvp` объединяет frontend, актуальную `ml` и необходимые изменения backend. `lead` и `ml-fixes` не включены: они имеют отдельную историю, а сравнение поиска на их синтетическом наборе не подтверждает превосходство на реальном каталоге. Результат — интегрированная кодовая база, не готовый рекомендательный MVP.

## Схемы и БД

`app.database.base.Base` принадлежит событиям ML; `ProductBase` и `app.database.Base` принадлежат прежним моделям backend. Это разные SQLAlchemy metadata: у них разные таблицы `recommendation_impressions`. Держите их в разных базах PostgreSQL. `DATABASE_URL` не может указывать на `alfa_events` или `alfa_events_test`; событийный движок принимает только эти имена и `ALFA_EVENTS_DATABASE_URL`. При каждом новом соединении дополнительно проверяется `current_database()`: псевдоним прокси, ведущий в БД с другим именем, отклоняется. Это не заменяет изоляцию ролей и прав: при развёртывании используйте отдельные базы и учётные записи с доступом только к своим данным. Не используйте исходную БД организаторов ни для одной из них.

Продуктовая цепочка `backend/product-alembic.ini` создаёт отдельную первоначальную схему пользователей, курсов и прежних моделей backend. Событийная цепочка `backend/alembic.ini` сохраняет существующие ревизии ML 0001–0004. Не применяйте одну цепочку к базе другой и не считайте их миграцией существующих пользовательских данных. Созданные старые таблицы показов и взаимодействий не являются каноническими ML-событиями. Согласование пользователей, actor/session, карточек и транзакций — задача следующих этапов.

Для новой изолированной среды из корня проекта после настройки `.env`:

```bash
python -m pip install -r backend/requirements.txt -r backend/requirements-catalog.txt
cp .env.example .env
# Установите собственные локальные значения в .env; никогда не коммитьте файл.
set -a; source .env; set +a
docker compose up -d db
docker compose -f scripts/events.compose.yml up -d db
python -m alembic -c backend/product-alembic.ini upgrade head
python scripts/migrate_events.py
PYTHONPATH=backend uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Шаблон задаёт отдельные локальные порты 55438 (продуктовая БД) и 55437 (БД событий). Перед запуском убедитесь, что они свободны. Events compose создаёт отдельный тестовый экземпляр БД; приложение не должно использовать тестовую БД как рабочую. Значения ML-наград в старом разделе конфигурации не настраивают политику `RewardPolicy` из ML. Семантические веса и архивы организаторов хранятся вне Git; предоставленные локальные файлы пока не проверены на совместимость с индексом.

```bash
cd frontend
npm ci
npm test
npm run build
npm run dev
```

На данном этапе доступны backend-маршруты пользователей и курсов и `/health`; старые маршруты рекомендаций и взаимодействий возвращают 503. Предыдущее решение создавало фиктивные оценки и неподтверждённые покупки, поэтому оно не включено в работу приложения. Frontend остаётся в явно обозначенном деморежиме; сетевой вызов ML и события не реализованы. Маршруты backend не имеют полноценной аутентификации и авторизации, пригодны только для локальной разработки.

## Проверки

Для ML-тестов нужен изолированный PostgreSQL `alfa_events_test`, заданный `ALFA_EVENTS_TEST_DATABASE_URL`. Проверки продуктовых миграций и API дополнительно требуют `ALFA_PRODUCT_TEST_DATABASE_URL` с именем базы `alfa_product_test`. Тесты создают временные схемы и удаляют только их. Например, после создания обеих тестовых БД на изолированном сервере:

```bash
OPENBLAS_NUM_THREADS=1 python -m pytest backend/tests -q
npm --prefix frontend test
npm --prefix frontend run build
```

Без тестовых URL часть проверок будет пропущена. Для этапа 2 выполнены тесты ML и событий, новые проверки продукта, обе миграции на чистых БД, HTTP health и ответы 503, сборка и тесты интерфейса. E2E рекомендаций, связка frontend–ML, обучение на пользовательских событиях и воспроизведение качества на реальном каталоге не проверялись и относятся к последующим этапам.

## Ревью этапа 2

Критик в роли lead backend engineer сначала оценил переданные фрагменты на 7/10 и указал риск псевдонимов БД. Добавлены проверка `current_database()` на новом соединении и отрицательный тест; повторная оценка — 8/10. Критик отметил необходимость последующей проверки изоляции ролей/прав PostgreSQL и выбранного proxy. Независимо прочитать файлы и запустить тесты ему не удалось: окружение не запускает sandbox без `bwrap`, запрос эскалации был прерван. Поэтому оценка относится к предоставленным фрагментам и результатам, а не к самостоятельной верификации кода.

Итоговый локальный прогон: 248 тестов backend/ML прошли, 1 пропущен из-за неподготовленного реального токенизатора; frontend — 8 тестов и успешная сборка. Продуктовая и событийная миграции применены к раздельным тестовым базам и повторены, `alembic check` продуктовой схемы успешен; роль тестовой PostgreSQL была общей для обеих БД, изоляция полномочий не проверялась.
