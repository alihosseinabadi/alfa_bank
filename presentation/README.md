# Альфа-Курс — материалы защиты

`product.html` — продуктовый one-pager на 9 страниц A4, `Alfa-Kurs-product-2026-11-17.pdf` — его PDF-версия для отправки. Это не презентация процесса разработки: страницы показывают работающий сценарий — вход, чат-анкету, разбор профиля, дашборд с вопросом дня, подборку, наставника, аналитику и профиль.

Скриншоты лежат в `presentation/shots/` и сняты с локального Docker-стека (`http://localhost:5173`). Интерфейс настоящий; каталог, названия, цены и длительности — синтетические. Запуск по-прежнему один:

```bash
cp .env.example .env && docker compose up --build
```

## Что проверять перед выступлением

1. Поднять стек на чистом окружении и открыть `http://localhost:5173`.
2. Пройти сценарий: «Войти в демо» → чат-анкета → разбор профиля → дашборд → подборка → наставник → аналитика → профиль. Это ровно те экраны, что на страницах 3–8.
3. В наставнике проверить запрос своими словами, например «Хочу стабильный поток клиентов» или «Помогите с налогами», и бессмысленный запрос — он должен вернуть уточнение, а не перезаписать цель. В мете ответа видно `hybrid-bm25-dense-prior-linucb-v1`, dense-модель (64D) и состояние LinUCB: `cold start` или `warm` с числом наград.
4. Сверить подписи «синтетические данные» и «оценка профиля · не ML» на скриншотах с текущей сборкой.
5. Пересобрать PDF после правок:

```bash
"C:\Program Files\Google\Chrome\Application\chrome.exe" --headless=new \
  --disable-gpu --no-pdf-header-footer --virtual-time-budget=8000 \
  --print-to-pdf="presentation/Alfa-Kurs-product-2026-11-17.pdf" \
```

Проверка покрытия запросов воспроизводится так:

```bash
python scripts/evaluate_demo_queries.py --json reports/demo_query_eval.json
```

Скрипт прогоняет 100 синтетических русских задач из `data/synthetic/retrieval_cases_v2.json` по реальному демо-индексу. Он показывает, сколько задач вообще находит материал, какие формулировки остаются без ответа и что пустые/OOV-запросы не дают ложных совпадений. Это диагностика покрытия, а не оценка релевантности: судейских разметок в наборе нет.

## Короткие ответы на вопросы жюри

**Почему BM25 и плотные векторы вместе?** BM25 объясним и точен на русской морфологии: видно, какие слова запроса совпали с публичным фрагментом; Snowball-стемминг, стоп-слова и бизнес-тезаурус связывают «нанять» с «наём», а «заявки» — с «клиентами». Плотный канал (TF-IDF → SVD, 64D) добавляет близость по смыслу и обучается на том же публичном корпусе — по тексту фрагмента вместе с описанием, темами и тегами материала. Каналы нормируются на свой максимум и объединяются 60/40, поэтому запрос может найти материал и по словам, и по вектору, а шкала BM25 не подавляет косинус. Веса приватной E5-модели не поставляются; `e5_retriever.py` готов заменить энкодер без изменения fusion и ранжирования.

**Что происходит без истории?** Контекст строится из явно заданной задачи и профиля. Если совпадения нет, наставник задаёт уточняющий вопрос и не подменяет цель профиля. Это проверено на пустых и бессмысленных запросах.

**Почему задача важнее истории?** Она отражает намерение сейчас. Поэтому новая формулировка обновляет цель профиля и пересчитывает подборку, а прошлые интересы остаются лишь одним из сигналов.

**Какие результаты уже доказаны?** Доказана работа компонентов: реальный BM25-поиск по демо-каталогу, русская нормализация, ранжирование, запись событий, интерфейс. Покрытие — 89 из 89 оцениваемых нормальных задач на синтетическом наборе; это не качество ранжирования и не эффект для бизнеса. Сравнение с baseline и влияние на конверсию остаются планом.

**Что с приватностью?** Приватные выгрузки и персональные данные не публикуются и не отправляются во внешние API. В демо нет реальных клиентских записей; профиль хранится локально в браузере.

**Почему в подборке есть материалы с «~profile fit»?** Это честный fallback полного каталога: гибридный поиск нашёл не всё, остальное показано ниже с явной пометкой «оценка профиля · не ML». Такие строки никогда не выдаются за score модели.
